## 1. 오늘 새로 만든 것: 오름 추천 MCP 서버

사용자가 제공한 참고 샘플(`sample_MCP/`, `sample_MCP2/etri-jejuax-example-mcp/` — FastAPI를 `FastMCP.from_fastapi()`로 감싸 streamable-http로 노출하는 패턴)을 그대로 따라 `oreum_mcp/`를 신규 구축했습니다.

| 파일 | 역할 |
|---|---|
| `oreum_mcp/app.py` | FastAPI → MCP 변환, `/health`, argparse(포트 기본 11010) |
| `oreum_mcp/modules/data.py` | `data/oreum.json` 읽기 전용 로더(요청마다 새로 읽음), `find_oreum`(id/이름 조회, 모호하면 후보 반환), `is_official_parking`(CSV vs 좌표 교차판단) |
| `oreum_mcp/modules/routes.py` | 도구 3개 정의 |
| `oreum_mcp/modules/shared.py` | 샘플과 동일한 `create_base_app` |
| `oreum_mcp/Dockerfile`, `docker-compose.yml`, `.env.example`, `requirements.txt` | 컨테이너 배포용 (샘플 구조 그대로, `OREUM_DATA_PATH` 환경변수로 컨테이너 내부에서 `data/oreum.json` 경로 오버라이드) |
| `oreum_mcp/test_tools.py` | 도구당 10개, 총 30개 회귀 테스트 |

**도구 3개** (사용자가 우선순위로 고른 기능):
1. `recommend_oreum` — 지역/난이도/거리/소요시간/계절/키워드/개방여부로 필터링 추천
2. `get_oreum_detail` — 이름 또는 id로 상세 조회 (좌표는 개수가 아니라 실제 값 반환)
3. `recommend_linked_oreums` — `notes.linked_oreums` 기반 연계 코스 추천

이 서버는 **읽기 전용**입니다 — `data/oreum.json`에 쓰지 않고, map_editor가 계속 수집하는 동안 서버 재시작 없이 최신 상태를 반영하도록 매 요청마다 파일을 새로 읽습니다.

## 2. 오늘 발견하고 고친 버그/설계 문제

실제 클라이언트로 도구를 호출해가며 나온 문제들입니다. 전부 이 세션 안에서 원인 파악 후 수정·재검증까지 완료했습니다.

| # | 문제 | 원인 | 조치 | 파일 |
|---|---|---|---|---|
| 1 | `recommend_linked_oreums`가 실제 존재하는 오름인데도 못 찾음 | `notes.linked_oreums`에 "큰노꼬메"/"작은노꼬메"라는 구어체 이름이 들어있는데(CSV `raw_note` 원문부터 그렇게 적혀있었음), 정식 오름명은 "노꼬메큰오름"/"노꼬메족은오름" — 이름이 달라 매칭 실패 | `data/oreum.json`에서 궷물오름/노꼬메족은오름 두 레코드의 `notes.linked_oreums` 3건을 정식 명칭으로 직접 교정 | `data/oreum.json` |

| 5 | `max_climb_time_min`에 `"30분"` 입력 시 `422` | 단위 붙은 문자열을 숫자로 못 바꿈 | 같은 validator에서 숫자 필드(`max_distance_km`, `max_climb_time_min`)는 정규식으로 앞의 숫자만 추출하도록 확장 (`"30분"`→30, `"1.5km"`→1.5) | 〃 |
| 6 | `region: "서귀포"`로 검색하면 결과 0건 | 실제 데이터 값은 정확히 `"서귀포시"`인데 필터가 완전일치라 "시"를 뺀 입력이 전부 걸러짐 | 완전일치 → 부분일치로 완화. 이후 사용자가 "한림주변" 같은 자연어 지명도 걸러야 한다고 지적 → 아예 `region`(제주시/서귀포시) 대신 **`address` 전체 문자열**에 대해 부분일치하도록 재설계(주소에 읍/면/동까지 다 들어있어서 "한림"/"구좌"/"표선" 같은 세부지명도 자동으로 커버됨) | 〃 |
| 7 | Inspector가 `"Session not found"` 에러 | 개발 중 서버를 반복 재시작하면서 streamable-http의 세션 상태가 매번 무효화됨 | 이 서버 도구는 전부 무상태 조회라 세션이 필요 없음 → `mcp.http_app(..., stateless_http=True)`로 전환, 재시작해도 세션 문제 자체가 없어지게 함 | `oreum_mcp/app.py` |
| 8 | `recommend_oreum`을 인자 없이(`{}`) 호출하면 `422` | FastAPI가 Pydantic 모델 바디 파라미터를 기본적으로 필수 취급 — 필드가 전부 optional이어도 바디 자체가 없으면 막힘. "필터 없이 그냥 추천해줘"처럼 LLM이 무인자 호출할 때 실제로 터질 수 있는 버그 | 라우트 함수 시그니처에 기본값 부여: `def recommend_oreum(request: RecommendRequest = RecommendRequest())` | 〃 |
| 9 | `access_open_only=True`가 원하는 대로 안 걸러짐 (아래 3절 참고) | 최초엔 "제한 상태거나 미분류(null)면 통과"였다가, 안전 우선 요청에 "open만 통과"로 과잉수정 → 결과가 329개 중 1개로 급감 | 최종적으로 **"명시적으로 제한 확인된(reservation_required/restricted/prohibited) 것만 제외, null/open은 통과"**로 재조정 — 실사용 가능한 결과 수를 유지하면서 확실히 위험한 곳만 제외 | 〃 |

### 그 외 (MCP 서버와 직접 관련은 없지만 같은 세션에서 처리)

- **`save_records()` 원자적 쓰기 적용** — 어제 보고서 "다음 작업 우선순위"에서 [높음]으로 올렸던 항목. `map_editor/app.py`에서 `open(path, "w")` 직접 덮어쓰기 → 임시파일에 쓰고 `os.replace()`로 교체하는 방식으로 변경, 동시 요청 시 JSON 파싱 에러 리스크 제거 (커밋 `074a301`).
- **오름 등산로 난이도 계산 스크립트** (`scripts/compute_trail_difficulty.py`, `compare_difficulty.py`, `analyze_mismatch.py`) — Copernicus DEM(`output_hh.tif`)으로 고도를 입히고 경사 기반 난이도 점수를 계산하는 1차 버전을 만들었으나, **사용자가 "난이도 계산은 내가 직접 디벨롭하겠다"고 판단**해 이 공식은 MCP 서버에 아직 반영하지 않았습니다. 개발 도중 `interpolate_path()`의 거리 계산 버그(정점 경계에서 거리 중복 가산 → 총거리 +8% 부풀려짐)를 발견해 수정했고, 국립공원공단 공식 등급표(PDF)와 대조해 현재 공식의 한계(avg_slope 미반영, total_gain 미정규화로 "완만하지만 긴 코스"가 "가파른 짧은 코스"보다 높은 점수를 받는 역전 현상 등)를 분석해 전달했습니다. **코드는 남겨뒀지만 서버 데이터에는 반영 안 함.**

## 3. `access_open_only` 관련 방향 수정 (제가 처음에 잘못 짚은 부분)

이 항목은 별도로 짚어야 할 것 같습니다. 사용자가 "제한 있으면 무조건 탈락시켜, 안전이 우선이야"라고 요청했을 때, 저는 이를 "명시적으로 'open'이 확인된 것만 통과"로 과잉 해석해서 구현했습니다. 실제 데이터를 까보니 **`access.status`가 명시적으로 `"open"`인 오름은 329개 중 단 1개**뿐이라(나머지는 제한 상태이거나 아예 미분류), 이 로직대로면 필터를 켜는 순간 추천 결과가 사실상 1개로 붕괴하는 문제가 있었습니다. 사용자가 "open 빼고 다 없애지 말라"고 바로 잡아줘서, "확실히 제한이 확인된 것만 제외, 미확인은 포함"으로 되돌렸습니다.

**교훈**: "안전 우선"이라는 원칙과 "무엇을 모를 때 어떻게 할지"는 별개의 질문입니다. 다음에 비슷한 안전/제한 필터를 만들 때는, 코드를 먼저 짜기 전에 실제 데이터 분포(이번 경우 `status` 값별 개수)부터 확인하고 사용자에게 결과 건수 영향을 미리 보여드리는 게 좋겠습니다.

## 4. 테스트 커버리지

`oreum_mcp/test_tools.py`에 도구당 10개, 총 30개 테스트 케이스를 작성했고 전부 통과합니다 (`python test_tools.py` → `총 30개 중 PASS 30, FAIL 0`).

| 도구 | 커버한 케이스 |
|---|---|
| `recommend_oreum` | 무인자 호출, region 정확/부분일치, difficulty, 단위 붙은 숫자(`"30분"`, `"1.5km"`) 파싱, season, 빈 문자열 전체, `access_open_only`, 매칭 0건 |
| `get_oreum_detail` | 이름/id 조회, 존재하지 않는 이름, 모호한 이름(후보 목록), `official` 플래그, `restroom_coord` null, 입구/등산로 복수 개, `notes` 유무 |
| `recommend_linked_oreums` | 정상 resolve, 연계정보 없음, 존재하지 않는 이름, 모호한 이름, id 조회, 역방향/상호 참조 |

이 저장소엔 아직 pytest 등 정식 테스트 프레임워크가 없어서, `fastmcp.Client`로 실행 중인 서버에 실제 MCP 호출을 날리는 스크립트 형태로 작성했습니다(서버가 떠 있어야 실행 가능).

## 6. Claude Code에게 명령할 때 발생한 문제점

- **26→27번이 이번 세션에서 유일하게 재작업이 필요했던 지점**입니다. "안전이 우선"이라는 짧은 지시를 제가 "미확인 상태도 위험하다고 간주해서 배제"로 확대 해석했는데, 실제로는 "확실히 위험하다고 확인된 곳만 배제하라"는 뜻이었습니다. 원인은 제가 코드를 먼저 고치고 나서야 실제 데이터 분포(결과 1개)를 보여드린 것 — **데이터 분포부터 먼저 보여드리고 그 다음에 어느 쪽으로 구현할지 여쭤봤다면** 한 번에 끝났을 자리입니다.
- 그 외 명령들은 대부분 "에러 로그/스크린샷 붙여넣기 → 원인 진단 → 수정 → 재검증" 흐름이 한 번에 끝났고, 재지시가 필요한 경우는 없었습니다.
- **다음에는 이렇게 명령하면 좋습니다**: 안전/제한/필터링처럼 "모호할 수 있는 원칙"을 지시할 때는 "이렇게 하면 결과가 몇 개나 남아? 먼저 보여줘"라고 덧붙이면, 극단적으로 과소/과잉 필터링되는 상황을 미리 걸러낼 수 있습니다.

## 8. 전체 요약

**오늘 가장 중요한 성과**
- 이 저장소에 없던 **MCP 서버(`oreum_mcp/`)를 처음부터 구축**하고, 조건 추천/상세조회/연계추천 도구 3개를 실제 클라이언트로 붙여 검증까지 완료했습니다.
- 개발 중 발견한 버그 9건(연계 오름 이름 불일치, 좌표 개수→실좌표 개편, 비공식 주차장 플래그, 빈 문자열/단위 파싱, 지역 부분일치, 세션 무효화, 무인자 호출, 안전필터 과잉/과소)을 전부 그 자리에서 고치고 재검증했습니다.
- 어제 [높음] 우선순위였던 `save_records()` 원자적 쓰기를 오늘 처리했습니다.
- 30개 회귀 테스트(`test_tools.py`)를 만들어 지금까지 고친 버그들이 다시 재발하지 않는지 확인할 수 있는 장치를 마련했습니다.

**현재 가장 큰 문제**
- 등산로 난이도 계산(경사도 기반 점수 공식)은 여러 결함(avg_slope 미반영, 거리 미정규화로 인한 역전 현상)이 있다고 분석까지 마쳤지만, **사용자가 직접 디벨롭하기로 해서 아직 서버 데이터에 반영되지 않은 상태**입니다. `recommend_oreum`의 `difficulty` 필터는 지금 CSV 원본 값(전체 41.6% 결측)만 쓰고 있습니다.
- `access_open_only` 필터는 "확실한 제한만 배제"로 안정화됐지만, 이는 데이터가 대부분 미분류(`notes` 143건 null + 분류된 186건 중에도 access 미기재 다수)라서 나온 실용적 타협이지, 실제 안전성을 보장하는 수준은 아직 아닙니다.

**다음 작업 우선순위**
- [높음] 난이도 계산 공식 재설계(사용자 진행 중) 완료되면 `recommend_oreum`/`get_oreum_detail`에 반영
- [중간] `access.status`/`trail_condition` 미분류 143건(+ 분류됐지만 access 미기재 다수) 지속 보강 — 그래야 `access_open_only`가 실질적으로 의미있어짐
