## 5. Claude Code에게 명령할 때 발생한 문제점

1. **"좌표로 표시 안되니??" 이슈가 미해결로 남음** — 원인: 진단 중 curl 도구 사용이 반려되었고, 곧이어 다른 기능 요청(진행률 대시보드)이 들어오면서 자연스럽게 우선순위가 밀려 다시 다뤄지지 않았습니다. → 다음에는: 버그 리포트 후 다른 요청으로 넘어가더라도, 이전 이슈가 미해결 상태임을 명시적으로 짚어주시면(또는 "이건 나중에 다시 보자"라고 표시) 놓치지 않습니다.
2. **404 반복 오류의 근본 원인이 확증되지 않음** — "서버 재시작 중 요청이 끊겼을 것"이라는 추정으로 마무리했고, 실제 재현 절차나 브라우저 콘솔 로그는 요청하지 않았습니다. → 다음에는: 같은 문제가 재발하면 브라우저 개발자 도구 Network 탭 캡처나 정확한 재현 순서(무엇을 클릭한 직후였는지)를 요청하면 더 정확히 진단할 수 있습니다.
3. **서버 프로세스 충돌이 여러 번 발생** — Claude가 검증용으로 띄운 서버와 사용자가 터미널에서 직접 띄운 서버가 8010 포트를 두고 반복적으로 충돌했습니다. 매번 확인 질문을 거쳐 처리했지만 흐름이 여러 번 끊겼습니다. → 이 부분은 이미 잘 지켜지고 있어(항상 사전 확인) 특별히 바꿀 필요는 없지만, 검증이 꼭 필요하지 않은 작은 변경은 curl 없이 코드 리뷰만으로 넘어가는 것도 방법입니다.
4. **스키마 변경이 두 번에 나뉘어 진행됨** — 처음엔 `trails` 배열화만 요청하셨다가, 곧이어 "입구도 여러 개"라는 요구사항이 추가로 나오면서 두 번째 대규모 마이그레이션(`entrances` 배열화)이 필요해졌습니다. → 다음에는: 데이터 구조를 바꾸는 요청을 하실 때 "이것도 나중에 여러 개가 될 수 있나?" 같은 인접 필드까지 한 번에 알려주시면 마이그레이션을 한 번에 합칠 수 있어 더 효율적입니다.

## 7. 전체 요약

### 오늘 가장 중요한 성과
1. 등산로/입구를 오름당 **여러 개** 저장·동시 표시할 수 있도록 데이터 구조(`trails[]`, `entrances[]`)와 API, 편집기 UI를 전면 개편했습니다.
2. 328건 전체에 대해 **수집 진행률을 실시간으로 확인**할 수 있는 대시보드(상단 패널 + 목록 배지)를 구현했습니다.
3. 세션 동안 사용자가 실제로 입구 27건, 주차장 19건, 화장실 6건, 등산로 28건의 신규 좌표/경로를 확보했습니다(테스트 데이터 아님, 파일에 실제 반영됨).

### 현재 가장 큰 문제
1. `migrate_entrances_and_drop_trail_start.py`가 재실행 시 오늘 수집한 입구 데이터를 전부 삭제할 수 있는 결함이 코드에 남아 있습니다.
2. `coordinates.restroom`(97.9% 결측)과 `trails[].surface_type`(97.3% 결측)이 사실상 비어 있어, 화장실 정보와 향후 난이도 스코어링 모두 사용 불가 수준입니다.
3. "좌표로 표시" 기능이 실제로 동작하는지 확인되지 않은 채 남아 있습니다.

### 데이터 상태
- **전체 데이터 규모**: 328건 (오름 레코드), `data/oreum.json` 약 846KB.
- **주요 데이터**: 기본정보(CSV 원본, 거의 완비) + 좌표/등산로(map_editor 수집, 대부분 미착수).
- **평균/전체 결측률**: map_editor 핵심 4항목(입구/주차장/화장실/등산로) 평균 **85.9% 결측**.
- **가장 결측률이 높은 데이터**: `coordinates.restroom.lat/lng` (97.9%, 7/328건만 존재).
- **데이터 품질상 가장 큰 문제**: `surface_type` 97.3% 결측으로, 문서화된 난이도 가중치 공식이 사실상 아직 적용 불가능한 상태.
