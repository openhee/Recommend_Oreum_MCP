### 1-2. 이번 대화 세션에서 Claude가 직접 수행한 변경

**① `CLAUDE.md` 문서 보강** — 목적: 코드에는 이미 있지만 문서화가 안 된 부분을 실제 코드(`map_editor/app.py`)와 대조해 채움.
- `GET /api/oreum`·`GET /api/oreum/progress`로 구성된 수집 진행률 대시보드(`compute_progress()`, `PROGRESS_FIELD_LABELS`, `collected`/`total` 배지, `#progress-summary` 패널)를 설명하는 문단을 새로 추가. 이 기능 자체는 어제(8/10) 리포트 1-5절에 이미 "오늘 만듦"으로 기록돼 있었는데, `CLAUDE.md`에는 그 설명이 누락돼 있던 것을 오늘 보완.
- 그 외 항목(파킹 배열, `note` 필드, OSM 후보 기능)은 `/init` 검토 시점에 이미 `CLAUDE.md`에 정확히 반영돼 있어 추가 수정 없음.

**② 진행률 바 CSS 버그 수정** — 사용자가 "진행률 바 4가지가 파랑색으로 퍼센티지에 맞게 채워지게 해"라고 요청 → 코드만 보고 "이미 그렇게 구현돼 있다"고 1차 답변했으나, 사용자가 실제 스크린샷(막대가 회색으로 비어 보임)을 제시하면서 재현된 **실제 버그**를 발견·수정.
  - **원인**: `map_editor/static/index.html`의 `renderProgressSummary()`가 `<span class="ps-bar-fill" style="width:${pct}%">`를 렌더링하는데, `.ps-bar-fill`에 `display` 속성이 없어 기본값인 `inline`으로 렌더링됨. 인라인 요소는 브라우저가 `width`/`height` 인라인 스타일을 무시하므로, 실제 채워진 비율과 무관하게 막대가 거의 안 보이는 상태였음.
  - **변경 전**: `#progress-summary .ps-bar-fill { height: 100%; background: #2b6cff; border-radius: 3px; }`
  - **변경 후**: `#progress-summary .ps-bar-fill { display: block; height: 100%; background: #2b6cff; border-radius: 3px; }` (`map_editor/static/index.html` 86번째 줄)
  - **검증**: Playwright/Chromium을 설치해 직접 스크린샷으로 재검증하려 했으나(백그라운드 설치는 완료, exit code 0), 코드 리뷰만으로 원인을 특정·수정한 뒤 사용자에게 하드 리프레시 후 재확인을 안내함 — **브라우저 렌더링으로 최종 확인은 아직 못 함(사용자 확인 대기)**.

**③ 서버 프로세스 충돌 대응** — 사용자가 `python map_editor/app.py`를 직접 실행했다가 `[Errno 10048]` 포트 바인딩 오류를 겪음(포트 8010이 이미 사용 중). `netstat`/`Get-Process`로 원인이 기존에 떠 있던 별도 python 프로세스(PID 5108, `C:\Users\user\miniconda3\python.exe`)임을 확인해 알려주고, 사용자 요청에 따라 `Stop-Process -Id 5108` 실행 → 사용자가 자신의 터미널에서 재기동하도록 안내.

## 5. Claude Code에게 명령할 때 발생한 문제점

1. **진행률 바 버그를 1차로 놓침** — 사용자가 "채우라고 했잖아"라는 표현을 쓸 정도로 이미 요청했던 사안인데(이번 대화 안에서는 처음 요청이었으므로, 대화 밖의 이전 세션에서 이미 한 번 요청했을 가능성이 있음), Claude는 코드만 읽고 "이미 구현돼 있다"고 결론 내렸습니다. 실제로는 `display: inline` 기본값 때문에 `width` 스타일이 브라우저에서 무시되는 버그가 있었습니다. → **다음에는**: "이미 이렇게 되어 있다"고 코드로 판단했더라도, UI 렌더링 관련 요청은 스크린샷/실제 브라우저 확인 없이 "이미 됨"이라고 단정하지 말고, 먼저 실제 화면을 확인하거나 최소한 "코드상으로는 맞는데 실제 렌더링을 확인 못 했다"고 명시해야 합니다.
2. **스크린샷 검증 도구가 준비 안 되어 있었음** — `chromium-cli`가 없어서 즉석에서 `pip install playwright` + `playwright install chromium`을 시도했고, 이 설치가 끝나기 전에 코드 리뷰로 먼저 버그를 찾아 수정했습니다. 결과적으로 이번엔 시간 손실 없이 해결됐지만, 설치가 오래 걸리는 작업이었다면 응답이 지연될 뻔했습니다. → **다음에는**: UI 검증이 필요할 걸 예상하면 세션 초반에 스크린샷 도구 가용 여부를 먼저 확인하는 것이 좋습니다(이번에 설치는 완료해뒀으므로 다음 세션부터는 바로 사용 가능).
3. **커밋이 세션 경계 없이 한 번에 몰려서 이루어짐** — 오늘 대화가 시작되기 전에 이미 파킹 배열화/`note` 필드/OSM 후보 기능이 코드에 들어가 있었는데, 이게 정확히 언제 어떤 세션에서 만들어졌는지는 git 히스토리(커밋 하나로 뭉침)나 이번 대화 기록으로 확인할 수 없었습니다. → **다음에는**: 기능 단위로 좀 더 자주 커밋해주시면, 다음 날 리포트를 작성할 때 "오늘 무엇이 새로 생겼는지"를 훨씬 정확하게 구분할 수 있습니다.
4. **서버 프로세스 충돌이 오늘도 재발** — 어제 리포트 5절에서 이미 지적된 문제(Claude가 검증용으로 띄운 서버 vs 사용자가 직접 띄운 서버가 포트 8010을 두고 충돌)가 오늘도 발생했습니다. 오늘은 사용자가 먼저 로그를 붙여넣어 알려줘서 빠르게 진단됐습니다. → 이 부분은 이미 사용자가 잘 알려주고 계셔서 특별히 개선할 점은 없으나, 계속 반복된다면 "검증용 서버를 띄우기 전에 항상 `netstat`으로 8010 사용 여부를 먼저 확인"하는 습관을 Claude 쪽에서 고정 루틴으로 만들 필요가 있습니다.

## 7. 전체 요약

### 오늘 가장 중요한 성과
1. 사용자가 map_editor를 통해 직접 대량의 신규 데이터를 확보했습니다 — 입구 +37건, 주차장 +36건, 화장실 +11건, 등산로 +39건(모두 오름 단위, 어제 최종 대비). map_editor 4대 핵심 필드 평균 결측률이 85.9% → 76.5%로 개선됐습니다.
2. 사용자가 재현 스크린샷으로 제보한 **진행률 바 미채움 버그**(`.ps-bar-fill`이 `<span>`이라 `width`/`height`가 브라우저에서 무시됨)를 코드에서 찾아 `display: block` 한 줄로 수정했습니다(`map_editor/static/index.html:86`).
3. `CLAUDE.md`에 문서화가 빠져 있던 수집 진행률 대시보드(`GET /api/oreum/progress` 등) 설명을 실제 코드와 대조해 보강했습니다.

### 현재 가장 큰 문제
1. 오늘 수정한 진행률 바 CSS 버그가 **실제 브라우저에서 정상 렌더링되는지 최종 확인이 안 된 상태**입니다(사용자의 하드 리프레시 후 확인 필요).
2. `trails[].surface_type` 결측이 98.3%(117개 중 115개)로 여전히(오히려 소폭 더) 심각해, 난이도 가중치 공식이 여전히 적용 불가능합니다.
3. `migrate_entrances_and_drop_trail_start.py`(어제부터)에 더해 오늘 새로 생긴 `migrate_parking_to_array_and_add_notes.py`도 재실행 시 데이터 손실 위험이 있는지 **코드 리뷰가 안 돼 있는 상태**입니다.

### 데이터 상태
- **전체 데이터 규모**: 328건 (오름 레코드), `data/oreum.json` 약 1.1MB(1,165,330바이트, 어제 846KB에서 증가).
- **주요 데이터**: 기본정보(CSV 원본, 거의 완비) + 좌표/등산로(map_editor 수집, 여전히 대부분 미착수이나 어제보다 개선).
- **평균/전체 결측률**: map_editor 핵심 4항목(입구/주차장/화장실/등산로) 평균 **76.5% 결측**(어제 85.9%에서 개선).
- **가장 결측률이 높은 데이터**: `coordinates.restroom.lat/lng` (94.5%, 18/328건만 존재) — 여전히 최악.
- **데이터 품질상 가장 큰 문제**: `surface_type` 98.3% 결측(117개 trail 중 115개)으로, 신규 trail 증가 속도를 입력 속도가 못 따라가고 있습니다.
